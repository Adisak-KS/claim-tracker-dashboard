## ทำไมเลือก Go

**เหตุผลหลักไม่ใช่ความเร็ว แต่คือไม่ต้องกลับมาเปลี่ยนภาษาทีหลัง**

การเปลี่ยนภาษาเป็นงานที่แพงที่สุด ต้องเขียนใหม่ทั้งระบบ ต่างจากการเปลี่ยน
ไลบรารีหรือเพิ่ม index ที่ทำระหว่างทางได้ เลือก Go ตั้งแต่แรกจึงเป็นการกันปัญหานั้น
พร้อมเผื่อกำลังไว้มากพอสำหรับกรณีที่ระบบขยายไปรับงานอื่นในอนาคต

ตัวเลขโหลดที่ประเมินไว้ (ดูหัวข้อถัดไป) ภาษาอื่นก็รับไหว การเลือก Go จึงเป็น
การซื้อพื้นที่เผื่อ ไม่ใช่การแก้ปัญหาที่มีอยู่จริงตอนนี้

**สิ่งที่แลกไป:** ใช้คนละภาษากับหน้าบ้าน (TypeScript) จึงแชร์ type ของสัญญา API
ตรง ๆ ไม่ได้ ต้องซิงก์เอง ระหว่างออกแบบวันเดียวสัญญาเปลี่ยนไปหลายรอบ
(เพิ่ม `sourceSystem`, `hnHash`, `cancelled` และตัด `Idempotency-Key` ออก)
ถ้าซิงก์ด้วยมือจะหลุดแน่นอน

🔴 **ทางแก้ที่ต้องทำตั้งแต่วันแรก: ใช้ OpenAPI spec เป็นต้นทางเดียว**
แล้ว generate type ทั้งสองฝั่งจากไฟล์นั้น ห้ามเขียน type ซ้ำสองที่ด้วยมือ

## โหลดที่ประเมินไว้

คำนวณจากข้อมูลจำลอง 5,013 หน่วยบริการ · 582,122 รายการต่อ 90 วัน
เฉลี่ยหน่วยละ 39 รายการต่อเดือน (ส่วนใหญ่เป็นคลินิกเล็ก ไม่ใช่โรงพยาบาลใหญ่)

| สถานการณ์ | โหลด |
|---|---|
| ทุกหน่วยกระจายส่งใน 1 ชั่วโมง | 1.4 req/s |
| 2,000 หน่วยส่งพร้อมกันใน 10 วินาที | 200 req/s |
| 2,000 หน่วยส่งพร้อมกันใน 1 วินาที | 2,000 req/s |

⚠️ **ตัวเลขนี้มาจากข้อมูลจำลอง ไม่ใช่ของจริง** ถ้าพบว่ามีโรงพยาบาลใหญ่
ที่ส่งวันละหลายหมื่นรายการ ต้องคำนวณใหม่

ตัวช่วยที่ทำให้โหลดไม่พุ่ง: ตอบ 202 ทันทีโดยไม่ประมวลผลก่อนตอบ แล้วเข้าคิว
งานหนักจึงไปอยู่ที่ worker ซึ่งทำงานตามจังหวะตัวเอง ไม่ผูกกับจำนวนคนที่ยิงพร้อมกัน

## คิวงาน: River ไม่ใช่ Redis

**BullMQ ใช้ไม่ได้** เป็นไลบรารีของ Node.js ล้วน ไม่มี client ฝั่ง Go ที่เข้ากันได้
(เคยอยู่ในข้อเสนอตอน stack ยังเป็น TypeScript พอเปลี่ยนเป็น Go จึงตกไป)

เลือก River ซึ่งเก็บคิวไว้ใน PostgreSQL แทน asynq ที่ต้องใช้ Redis

🔴 **เหตุผลหลัก: งานเข้าคิวกับงานเขียนข้อมูลอยู่ใน transaction เดียวกันได้**
ถ้าคิวอยู่คนละที่ จะมีช่องว่างที่เขียนฐานข้อมูลสำเร็จแล้วแต่ใส่คิวไม่ทันเพราะ Redis ล่ม
งานนั้นหายเงียบโดยไม่มีใครรู้ ข้อมูลเคลมที่หายแล้วกู้ไม่ได้คือความเสียหายถาวร
กับ River เป็นไปไม่ได้เพราะทั้งสองอย่าง commit พร้อมกัน

**ภาระที่เพิ่มให้ฐานข้อมูลน้อยมาก** ตอนรับเข้า River เขียนแค่ 1 แถวต่อ request
(บันทึกว่ามีงานรออยู่) ไม่ได้เขียนข้อมูลจริงตอนนั้น

| ที่พีคสุด (2,000 หน่วยพร้อมกันใน 1 วินาที) | |
|---|---|
| งานเข้าคิว | 2,000 INSERT/s |
| PostgreSQL รับได้ | 10,000-50,000 INSERT/s |
| ใช้กำลัง | ประมาณ 10% |

งานหนักจริง (78,000 แถว) ไปอยู่ที่ worker ซึ่งไม่ผูกกับจำนวนคนที่ยิง
ใช้ `COPY` เขียนเป็นชุดจะเคลียร์หมดใน 16 วินาที ระหว่างนั้นทุกหน่วยได้ 202 กลับไปแล้ว

**ที่ Redis ไม่ได้ช่วยจริง:** ต่อให้แยกคิวไปไว้ Redis พอฐานข้อมูลล่ม worker
ก็เขียนอะไรไม่ได้อยู่ดี งานแค่ไปกองอยู่อีกที่หนึ่ง ระบบหยุดเหมือนกัน

## 🔴 จุดที่พังจริงคือ connection pool ไม่ใช่คิว

ถ้าเปิด connection ต่อ request ที่พีคจะได้ 2,000 connection
แต่ PostgreSQL รับได้ราว 100-300 เท่านั้น **ตรงนี้พังก่อนเพื่อนเสมอ**
และพังไม่ว่าจะเลือกคิวแบบไหน

ต้องกัน 3 ชั้น เรียงตามลำดับที่ต้องทำ

| ชั้น | ทำอะไร | เมื่อไหร่ |
|---|---|---|
| pgx pool | จำกัด connection ไว้ 20-50 คำขอที่เกินให้รอคิว ไม่เปิดเพิ่ม | ตั้งแต่วันแรก ตั้งค่าบรรทัดเดียว |
| rate limit ต่อ API key | ปฏิเสธตั้งแต่ต้นทาง ดีกว่าปล่อยเข้ามาแล้วล่มทั้งระบบ | ตั้งแต่วันแรก |
| PgBouncer | ตัวคั่นหน้าฐานข้อมูล รวม connection หลายพันให้เหลือไม่กี่สิบ | เมื่อขึ้น production |

🔴 **rate limit ต่อ API key ไม่ใช่ต่อ IP** เพราะหลายหน่วยบริการอาจออกเน็ตทาง IP เดียวกัน

## Redis เหลืองานเดียว

ใช้ทำ rate limit ต่อ API key เท่านั้น ซึ่งเป็นงานที่ Redis เหมาะที่สุด
(นับเร็ว หมดอายุเอง ไม่ต้องเก็บถาวร)

🔴 **ไม่ใช้ cache ผลคิวรี** คิวรีเร็วพออยู่แล้ว (วัดได้ 20-105 ms)
การใส่ cache จะแลกมาด้วยปัญหาข้อมูลเก่าค้าง ซึ่งร้ายกว่าสำหรับระบบที่ตัวเลข
ต้องตรงกันทุกหน้า (เคยเจอมาแล้วตอนการ์ดสรุปกับตารางบอกเลขคนละชุด)

ถ้าวันหน้าคิวรีช้าจริง ให้แก้ที่ index หรือ materialized view ก่อน
เพราะทั้งสองอย่างไม่ทำให้ข้อมูลเก่าค้างโดยไม่มีใครรู้

**หมายเหตุเรื่อง license:** Redis เปลี่ยนไปใช้ RSALv2/SSPL ตั้งแต่ปี 2024
ถ้าองค์กรมีนโยบายห้ามใช้ license กลุ่มนี้ ให้เปลี่ยนไปใช้ Valkey (BSD เหมือน Redis เดิม)
ซึ่งเป็น fork ที่ Linux Foundation ดูแล ใช้แทนกันได้โดยไม่ต้องแก้โค้ดสักบรรทัด
เปลี่ยนแค่ตัวที่ติดตั้งบนเครื่อง

## ทำไม PostgreSQL ไม่ใช่ MySQL หรือ MongoDB

**ไม่เอา MongoDB** เพราะข้อมูลเราเป็นตารางที่มีความสัมพันธ์ชัดเจน
(หน่วยบริการ ไปยัง รายการเคลม ไปยัง ประวัติสถานะ) และต้องการความถูกต้อง
ของตัวเลขเป็นอันดับแรก ไม่ใช่ความยืดหยุ่นของ schema

สิ่งที่ต้องการซึ่ง PostgreSQL บังคับให้ได้แต่ MongoDB ต้องระวังเอง:

- กุญแจ `(hospital_code, source_system, vn)` ห้ามซ้ำ
- ยอดรวมต้องบวกกันลงตัวเสมอ (ต้องการ transaction เต็มรูปแบบ)
- นับยอดแยกเขต แยกประเภท แยกช่วงวัน (SQL `GROUP BY` ธรรมดา)

**JSON ไม่ใช่เหตุผลให้เลือก MongoDB** เพราะ PostgreSQL เก็บ JSONB ได้
พร้อมทำ index ได้ด้วย จึงเก็บ `errors[]` ดิบไว้ในคอลัมน์เดียวได้
โดยยังคง JOIN และบวกยอดแบบ SQL ได้ตามปกติ

**MySQL ใช้ได้จริง ไม่ได้แย่** แต่ PostgreSQL ชนะในจุดที่เราใช้พอดี
คือ JSONB ทำ index ได้ง่ายกว่า, `COPY` เขียนเป็นชุดได้เร็วกว่า (ตรงกับ worker),
ค้นภาษาไทยรองรับดีกว่า (ชื่อหน่วยบริการเป็นไทยทั้งหมดและมีช่องค้นทุกหน้า)
และถ้าวันหน้าข้อมูลโตจนต้องใช้ TimescaleDB ก็เปิดเป็น extension ได้
โดยไม่ต้องย้ายฐานข้อมูล

🔴 **ถ้าทีมที่ดูแลถนัด MySQL อยู่แล้ว ให้ใช้ MySQL** โหลดระดับนี้ MySQL รับได้สบาย
ฐานข้อมูลที่ทีมกู้คืนเป็นตอนตีสอง มีค่ามากกว่าข้อได้เปรียบทางเทคนิคที่อาจไม่ได้ใช้

## พื้นที่เก็บข้อมูล

วัดจากข้อมูลจริงในระบบจำลอง: `errors[]` เฉลี่ย 533 bytes ต่อรายการที่ติดปัญหา
(เฉลี่ย 1.5 รหัสต่อรายการ มากสุด 2)

| | ต่อปี |
|---|---|
| รายการทั้งหมด | 2,360,828 |
| ผ่าน (`errors` ว่าง) | 1,935,879 (82%) |
| ติดปัญหา | 424,949 (18%) |
| **พื้นที่รวม** | **0.65 GB** |
| ถ้าเก็บประวัติเฉลี่ย 3 ชั้นต่อรายการ | 1.95 GB |

JSON ของ error ไม่ใช่ภาระ เพราะ 82% ผ่านและมี `errors[]` เป็น array ว่าง

### ถ้าเก็บ `claimItems[]` ทั้งก้อนด้วย

เจ้าของงานตัดสินใจให้เก็บทั้งก้อน ตัวเลขจึงเปลี่ยนจากข้างบนมาก
เพราะ `claimItems[]` เป็นรายบรรทัดค่ารักษา ผู้ป่วยในที่นอนนานมีได้หลายร้อยบรรทัด

| กลุ่ม | จำนวน/ปี | ต่อรายการ | รวม |
|---|---|---|---|
| ผู้ป่วยนอก | 2,124,745 | 2.9 KB | 5.74 GB |
| ผู้ป่วยใน | 212,475 | 10.1 KB | 2.00 GB |
| ผู้ป่วยในรายใหญ่ | 23,608 | 37.7 KB | 0.83 GB |
| **รวม** | | | **8.57 GB/ปี** |

PostgreSQL บีบ JSONB ให้อัตโนมัติผ่าน TOAST เหลือราว **2.6 GB/ปี**
ซึ่งยังอยู่ในระดับที่จัดการได้สบาย แต่มากกว่าการเก็บแค่ยอดสรุปราว 4 เท่า

**เก็บ `claimItems[]` ได้ครบทุกฟิลด์** รวม `stdCode` ด้วย
(`billGrcs` `stdCode` `paidQty` `paidPerUnit` `totalPoint` `paidType`)

`stdCode` เป็นรหัสมาตรฐานของรายการที่เบิก จัดเป็นข้อมูลการเงิน ไม่ใช่ข้อมูลตัวบุคคล
ไม่เข้าข่ายรายการห้ามเก็บตาม CLAUDE.md ข้อ 2.1 (ชื่อ นามสกุล เลขบัตรประชาชน
ที่อยู่ เบอร์โทร วันเกิด รหัสวินิจฉัยที่ระบุตัวบุคคลได้ ผลตรวจ)
อยู่ในกลุ่มเดียวกับ `vn` และ `an` ที่กฎอนุญาตไว้แล้ว

ทำให้ตอบได้ทั้ง "หมวดไหนถูกตัดเงินบ่อย" และ "รายการไหนถูกปฏิเสธบ่อย"
ซึ่งเป็นข้อมูลที่ทีมฝึกอบรมเอาไปใช้ได้ตรง

## Index ที่ต้องมี

ออกแบบจากคิวรีที่หน้าจอยิงจริง ไม่ใช่เดาล่วงหน้า

| Index | รองรับอะไร |
|---|---|
| `UNIQUE (hospital_code, source_system, vn)` | กุญแจธรรมชาติ กันข้อมูลซ้ำตอนรับเข้า |
| `(hospital_code, submitted_at DESC)` | หน้ารายละเอียดหน่วยบริการ กรองช่วงวันที่ |
| `(submitted_at DESC) WHERE outcome = 'failed'` | หน้า "ที่ต้องแก้" ซึ่งเป็นค่าเริ่มต้น |
| `GIN (errors jsonb_path_ops)` | ค้นว่ารายการไหนติดรหัสอะไร |
| `(health_zone, province)` | ตัวกรองหน้ารายชื่อหน่วยบริการ |

🔴 **ตัวแรกสำคัญที่สุดและไม่ใช่เรื่องความเร็ว** มันบังคับไม่ให้ข้อมูลซ้ำเข้าระบบได้เลย
ต่อให้โค้ดฝั่งเราพลาด ฐานข้อมูลจะปฏิเสธให้ (ดูเหตุผลเรื่องกันซ้ำใน
[ingest-contract](../api/ingest-contract.md))

ตัวที่สามเป็น partial index สร้างเฉพาะแถวที่ไม่สำเร็จ (18% ของทั้งหมด)
เล็กและเร็วกว่า index เต็ม ตรงกับที่หน้าจอเปิดมาที่ "ที่ต้องแก้" เป็นค่าเริ่มต้น

⚠️ **อย่าใส่ index เกินจำเป็น** ทุก index ทำให้การเขียนช้าลง และงานนี้เขียนหนักกว่าอ่าน

## เครื่องมือที่ต้องมีตั้งแต่วันแรก

### goose (migration)

ห้ามแก้ schema ด้วยมือ เพราะพอมีหลายเครื่อง (dev, test, prod)
จะไม่มีใครรู้ว่าเครื่องไหน schema เป็นอย่างไร

เลือก goose เพราะ migration เป็นไฟล์ SQL ธรรมดา อ่านออกโดยไม่ต้องเรียนภาษาใหม่
ตรงแนวเดียวกับที่เลือก sqlc คือเขียน SQL จริงไม่ซ่อน

### oapi-codegen (แก้ปัญหาแชร์ type ข้ามภาษา)

🔴 **ตัวนี้สำคัญที่สุดในรายการ** เพราะเป็นทางแก้ผลข้างเคียงจากการเลือก Go

เขียน OpenAPI spec ครั้งเดียวเป็นต้นทาง แล้ว generate struct ฝั่ง Go ด้วย oapi-codegen
กับ type ฝั่งหน้าบ้านด้วย `openapi-typescript` **ห้ามเขียน type ซ้ำสองที่ด้วยมือ**

หลักฐานว่าจำเป็น: ระหว่างออกแบบวันเดียวสัญญาเปลี่ยนไป 5 รอบ
ถ้าซิงก์ด้วยมือจะหลุดแน่นอน

### golangci-lint

รวม linter หลายสิบตัวในคำสั่งเดียว จับ error ที่ไม่ได้เช็คซึ่งเป็นสาเหตุบั๊กอันดับต้น ๆ ของ Go
ต้องรันใน CI ไม่ใช่รันเฉพาะตอนนึกได้

### testcontainers-go

รัน PostgreSQL จริงใน Docker ตอนเทสต์

🔴 **จำเป็นเพราะ logic กันซ้ำของเราทดสอบด้วย mock ไม่ได้**
ทั้ง unique constraint และการเทียบ `errors[]` แบบไม่สนลำดับ ต้องมีฐานข้อมูลจริง
ถึงจะรู้ว่าทำงานถูกหรือไม่

### k6 (ทดสอบโหลด)

ใช้พิสูจน์ว่าตัวเลข 2,000 req/s ที่ประเมินไว้เป็นจริงหรือไม่
และหาว่า connection pool ตั้งเท่าไรถึงพอดี

## ข้อปฏิบัติที่ต้องทำตั้งแต่วันแรก

### 🔴 ทดสอบด้วยข้อมูลสเกลจริง ไม่ใช่ 10 แถว

ใส่ข้อมูลระดับ 2.3 ล้านแถวตั้งแต่วันแรก แล้ววัดว่าคิวรีที่หน้าจอใช้จริงเร็วแค่ไหน
คิวรีที่เร็วกับ 10 แถวอาจช้ามากกับล้านแถว และจะรู้ตอนขึ้น production แล้วซึ่งสายเกินไป

### 🔴 ห้าม log payload ดิบ

ถ้า log payload ตอน debug ข้อมูลผู้ป่วยจะไปโผล่ใน log แทน
และ log มักถูกส่งต่อไปที่อื่น (ระบบรวม log, ไฟล์สำรอง) โดยไม่มีใครคิดถึงเรื่องนี้

log ได้แค่: `hospitalCode`, `batchId`, จำนวนรายการ, รหัสข้อผิดพลาด
ห้ามมี `vn`, `hnHash`, เนื้อความจากผู้ป่วย หรือ payload ทั้งก้อน

### 🔴 API key ต้อง hash ก่อนเก็บ

เก็บแบบ hash เหมือนรหัสผ่าน ถ้าฐานข้อมูลรั่ว คนที่ได้ไปจะปลอมเป็นหน่วยบริการไหนก็ได้
และต้องออกแบบให้หมุนเวียน key ได้โดยไม่ต้องหยุดระบบ

**ผูก key กับ `hospitalCode` ให้แน่น** ถ้าไม่ตรงกันให้ปฏิเสธ
ไม่งั้นหน่วยหนึ่งจะส่งข้อมูลในนามของอีกหน่วยได้

### validate `hospitalCode` กับทะเบียนจริง ไม่ใช่แค่รูปแบบ

ตรวจ 2 อย่าง: ยาวไม่เกิน 9 ตัว และมีรหัสนี้ในทะเบียนที่ซิงก์มาหรือไม่

🔴 **ห้ามเขียน regex ตรึงตัวอักษรนำหน้า** เพราะกระทรวงเพิ่มตัวใหม่เรื่อย ๆ
ถ้าตรึงไว้แล้วเขาออกตัวใหม่ ระบบจะปฏิเสธข้อมูลจริงทิ้งโดยไม่มีใครรู้
(เหตุผลเต็มใน [ingest-contract](../api/ingest-contract.md))

### วัดตั้งแต่วันแรก ไม่ใช่ตอนมีปัญหา

เก็บอย่างน้อย 4 ตัว: เวลาตอบต่อ endpoint · ความยาวคิว · อัตราปฏิเสธ ·
จำนวนรายการที่ `unchanged`

ตัวสุดท้ายสำคัญ ถ้าสูงผิดปกติแปลว่าระบบต้นทางยิงข้อมูลเดิมซ้ำโดยไม่จำเป็น
ซึ่งจะไม่มีทางรู้เลยถ้าไม่วัด

⚠️ **อย่าเพิ่ง optimize ก่อนวัด** ตัวเลขที่ประเมินไว้บอกว่ายังห่างเพดานมาก
การใส่ cache หรือแบ่ง partition ตอนนี้จะได้ความซับซ้อนโดยไม่ได้อะไรกลับมา

## เครื่อง production

ลงบนเครื่องเดียว แยก container ตาม service ผ่าน docker compose
RAM ขั้นต่ำ 8 GB

### แบ่ง RAM 8 GB

| service | จอง | หมายเหตุ |
|---|---|---|
| PostgreSQL shared_buffers | 2 GB | 25% ของ RAM ทั้งเครื่องตามคำแนะนำมาตรฐาน |
| PostgreSQL อื่น ๆ (work_mem, connection) | 1 GB | |
| Go app | 512 MB | ตั้ง `GOMEMLIMIT` ให้ตรงกับค่านี้ |
| Redis | 256 MB | ใช้แค่ rate limit ไม่ได้เก็บคิว |
| OS และ Docker | 1 GB | |
| **เหลือให้ page cache และแกะ gzip** | **3.3 GB** | |

พื้นที่ที่เหลือแกะ payload ขนาด 20 MB พร้อมกันได้ราว 80 request
ซึ่งมากกว่า connection pool ที่จะตั้งไว้ (20-50) **RAM จึงไม่ใช่คอขวด**
pool จะกันไว้ก่อนเสมอ

### 🔴 แยก container ไม่ใช่ยัดรวมใน container เดียว

อยู่เครื่องเดียวกันได้ แต่ต้องแยก container ต่อ service

| เหตุผล | |
|---|---|
| restart app ไม่กระทบฐานข้อมูล | ถ้ารวมกัน restart ทีฐานข้อมูลดับด้วย |
| ตั้ง memory limit แยกได้ | รวมกันแล้วแย่ง RAM กันเอง |
| อ่าน log แยกกันได้ | |
| ย้ายฐานข้อมูลออกไปเครื่องอื่นทีหลังได้ | ไม่ต้องแก้โค้ด แค่เปลี่ยน connection string |

### 🔴 ต้องตั้ง memory limit ทุก container

ถ้าไม่ตั้ง แล้ว service ใดกินจนเต็ม ระบบปฏิบัติการจะฆ่า process
ที่กินหน่วยความจำมากที่สุดทิ้ง ซึ่งมักเป็น PostgreSQL เอง
ข้อมูลที่ยังไม่ commit จะหายทันทีโดยไม่มีสัญญาณเตือน

### 🔴 ต้องตั้ง `GOMEMLIMIT`

Go จะเลื่อนการเก็บกวาดหน่วยความจำออกไปจนกว่าจะถึงลิมิต
ถ้าไม่ตั้ง มันจะถือว่ามี RAM ทั้งเครื่องให้ใช้คนเดียว แล้วไปแย่งกับ PostgreSQL

### ค่า config ที่เป็นจุดตั้งต้น

| ค่า | ตั้งไว้ | ทำไม |
|---|---|---|
| `shared_buffers` | 2GB | 25% ของ RAM |
| `max_connections` | 100 | ไม่ต้องมาก เพราะ pool คุมอยู่แล้ว |
| pgx pool size | 20-50 | คอขวดจริงของระบบ ต้องวัดด้วย k6 หาค่าที่พอดี |
| `GOMEMLIMIT` | 512MiB | ต้องตรงกับ memory limit ของ container |
| request พร้อมกันสูงสุด | 50 | กันแกะ gzip พร้อมกันจน RAM หมด |

⚠️ **ตัวเลขเหล่านี้เป็นจุดตั้งต้น ไม่ใช่ค่าที่ยืนยันแล้ว** ต้องรัน k6
ด้วยข้อมูลสเกลจริงก่อนขึ้น production เพื่อหาค่า pool ที่พอดี
ตั้งน้อยไปจะคอขวด ตั้งมากไปจะแย่ง RAM กับ PostgreSQL

### เวลาตอบที่คาดไว้

| ขั้นตอนตอนรับ request | เวลา |
|---|---|
| แกะ gzip | ~20 ms |
| แปลง JSON | ~5 ms |
| ตรวจฟิลด์บังคับ | ~2 ms |
| เขียนคิว 1 แถว | ~3 ms |
| **รวม** | **~30 ms** |

งานหนักจริง (เขียนข้อมูลทุกบรรทัด) ไปอยู่ที่ worker ซึ่งทำทีหลัง
หน่วยบริการจึงไม่ต้องรอ

**ถ้าคิวยาวขึ้นเรื่อย ๆ แปลว่า worker ตามไม่ทัน** ตรงนั้นไม่ใช่ปัญหาความเร็ว API
(API ยังตอบ 30 ms เหมือนเดิม) แต่ข้อมูลบนหน้าจอจะล่าช้า ให้เพิ่มจำนวน worker
นี่คือเหตุผลที่ต้องวัดความยาวคิวตั้งแต่วันแรก

| ไม่ใช้ | เพราะ |
|---|---|
| Fiber, Gin หรือ framework อื่น | `net/http` ตั้งแต่ Go 1.22 มี routing ในตัวแล้ว ใช้ของมาตรฐานไม่ต้องพึ่ง dependency ที่อาจเลิกดูแล |
| ORM เต็มรูปแบบ | sqlc อ่าน SQL จริงแล้วสร้าง struct ให้ ได้ type safety โดยไม่ซ่อน SQL |
| GraphQL | มี endpoint เดียวกับหน้าจอไม่กี่หน้า เพิ่มชั้นแล้วไม่ได้อะไรกลับมา |
| microservices, Kubernetes | ระบบเล็กเกินกว่าจะคุ้มกับความซับซ้อน |
| Redis cache ผลคิวรี | คิวรีเร็วพออยู่แล้ว แลกมาด้วยปัญหาข้อมูลเก่าค้าง |
| BullMQ | เป็นไลบรารีของ Node.js เรียกจาก Go ไม่ได้ |
| asynq | ต้องพึ่ง Redis และงานอาจหายถ้า Redis ล่มหลัง commit |
| atlas | migration เป็น DSL ของตัวเอง สู้ไฟล์ SQL ที่อ่านออกเลยไม่ได้ และบางฟีเจอร์เสียเงิน |
| swag | ยังเป็น rc ตั้งแต่ ม.ค. 2569 และสร้าง spec จากโค้ดทีหลัง ทำให้ฝั่งหน้าบ้านตามไม่ทัน |
| validator | oapi-codegen สร้าง validation จาก spec ให้แล้ว ลงซ้ำจะได้กฎสองชุดที่อาจไม่ตรงกัน |
| Prometheus, Grafana | ยังไม่มีของให้วัด เริ่มจาก `log/slog` ที่มากับภาษาก่อน |
| TimescaleDB | โหลดยังห่างจากที่มันออกแบบมารองรับมาก เปิดเป็น extension ทีหลังได้โดยไม่ต้องย้ายฐาน |

⚠️ **River ยังเป็นเวอร์ชัน 0.x** API อาจเปลี่ยนได้ก่อนถึง 1.0
แต่อัปเดตสม่ำเสมอ (ล่าสุด 10 ก.ย. 2569) และมีคนใช้ใน production แล้ว
ถ้าไม่อยากพึ่งไลบรารีเลย เขียนคิวเองบน PostgreSQL ได้ด้วย
`SELECT ... FOR UPDATE SKIP LOCKED` ซึ่งโหลดระดับนี้ทำได้สบาย

## คนดูแล

ทีม BMS เขียนและดูแลเองทั้งหน้าบ้านและหลังบ้าน ไม่ได้จ้างข้างนอก

มีผลกับการตัดสินใจ 2 ข้อ

**1. ยิ่งต้องใช้ OpenAPI spec เป็นต้นทางเดียว** เพราะคนกลุ่มเดียวกันสลับไปมา
ระหว่าง Go กับ TypeScript ถ้าต้องจำเองว่า field ไหนเปลี่ยนไปแล้วบ้าง จะพลาดแน่นอน
ให้เครื่องมือจำแทน

**2. เลือกของมาตรฐานให้มากที่สุด** ทีมเล็กไม่มีเวลาตามแก้ไลบรารีที่เลิกดูแล
จึงเป็นเหตุผลที่ใช้ `net/http` แทน framework และใช้ `log/slog` ที่มากับภาษา
