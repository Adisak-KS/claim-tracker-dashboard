## 2026-09-12 · ใช้รหัสสถานะและรหัสข้อผิดพลาดจริงของ สปสช.

**ตัดสินใจ:** ยึดตาม API Specification 13Plus v1.3.5.1
คือ 66 รหัสสถานะ และ 654 รหัสข้อผิดพลาด

**ทำไม:** ตอนแรกออกแบบเองจากฝั่ง HOSxP ได้แค่ 4 สถานะ (`Y/N/C/ว่าง`)
กับรหัสปัญหาที่ตั้งเอง 8 ตัว พอได้เอกสารจริงพบว่า

- สถานะจริงมี lifecycle 7 ขั้น ตอบได้ว่า "เงินค้างอยู่ขั้นไหน" ไม่ใช่แค่ "ผ่านไหม"
- รหัสข้อผิดพลาดจริงมีวิธีแก้ที่ สปสช. เขียนไว้ให้แล้ว ไม่ต้องแต่งเอง
- มีธง AllowClaim บอกว่าแก้แล้วส่งใหม่ได้ไหม ซึ่งเป็นข้อมูลที่คิดเองไม่ได้

**ไม่เอา:** ใช้รหัสที่ตั้งเอง (ผิดจากของจริง และไม่มีวิธีแก้)

**ผลข้างเคียง:** รหัส `5102` ที่เคยติดป้ายว่า "ตีกลับ" ผิด
ของจริงคือ "ไม่ตรงเงื่อนไขสิทธิ์ OFC, LGO, BKK, UCS"

## 2026-09-12 · จัดกลุ่มรหัสข้อผิดพลาดแทนการเรียงทั้ง 654 รหัส

**ตัดสินใจ:** หน้าปัญหาแสดง 2 ชั้น
ชั้นบนเป็นกลุ่มใหญ่ตามตัวอักษรนำหน้า (C, G, D, S, ...) ชั้นล่างเป็นรหัสย่อย

**ทำไม:** 654 รหัสเรียงเป็นลิสต์เดียวไม่มีใครอ่านจบ และไม่รู้ว่าต้องแก้อะไรก่อน
ตัวอักษรนำหน้าสื่อความหมายอยู่แล้ว (C = รหัสเบิก, G = สิทธิ, D = อุปกรณ์)
ผู้บริหารดูชั้นบนพอ ทีมฝึกอบรมกดเข้าไปดูชั้นล่าง

**ไม่เอา:** แสดง 10 อันดับแรกอย่างเดียว (ซ่อนปัญหาที่กระจายในหลายรหัสย่อย)

## 2026-09-12 · แยกรายงานตามธง AllowClaim

**ตัดสินใจ:** นับรายการที่ `AllowClaim = N` แยกจาก `Y`

**ทำไม:** สองอย่างนี้คนละความหมายทางธุรกิจสิ้นเชิง

- `Y` = งานที่รอแก้ ยังมีโอกาสได้เงิน
- `N` = เงินที่หายไปแล้ว แก้ไม่ได้ ต้องอุทธรณ์หรือปล่อย

ถ้าเอามารวมกันเป็น "ส่งไม่สำเร็จ" ก้อนเดียว ผู้บริหารจะไม่รู้ว่าเสียเงินไปเท่าไร

## 2026-09-12 · ไม่ใช้ ClickHouse ใช้ PostgreSQL กับ TimescaleDB

**ตัดสินใจ:** Phase 2 จะใช้ PostgreSQL + TimescaleDB

**ทำไม:** โหลดจริงประมาณ 25 ล้านแถวต่อวัน เฉลี่ยราว 290 แถวต่อวินาที
TimescaleDB รับได้ 100,000 ถึง 500,000 จุดต่อวินาที เหลือเฟือ
และได้ข้อมูลเชิงสัมพันธ์ (ผู้ใช้ สิทธิ์ API key) อยู่ที่เดียวกัน

**ไม่เอา:** ClickHouse (แรงเกินจำเป็น และเสียความสัมพันธ์เชิงตาราง)

**ตรวจสอบเมื่อ:** 2026-09-12

## 2026-09-12 · ป้องกันการนับซ้ำด้วย idempotency key

**ตัดสินใจ:** API รับข้อมูลต้องมี idempotency key ต่อ batch

**ทำไม:** อ่านโค้ดส่งเคลมฝั่ง HOSxP แล้วพบว่า chunk ที่ส่งไม่สำเร็จ
จะถูกนับเป็น error แล้ว**ส่งใหม่ได้** (ดู `cxButton10Click`)
ถ้าไม่มี key กันไว้ โรงพยาบาลที่ลองส่งซ้ำจะทำให้ยอดตัวเองพองขึ้นเอง
แล้วตัวเลขในแดชบอร์ดจะเชื่อถือไม่ได้ทั้งระบบ

## 2026-09-12 · รับข้อมูลแบบ batch ไม่ใช่ทีละรายการ

**ตัดสินใจ:** API รับเป็นชุด ไม่ใช่ยิงทีละรายการ

**ทำไม:** โค้ดฝั่ง HOSxP ทำ SignOn ครั้งเดียวต่อ batch แล้วส่งเป็น chunk ละ 10 ราย
(ข้อจำกัดของ สปสช.) แปลว่าระบบต้นทางคิดเป็นชุดอยู่แล้ว
ถ้าให้ยิงทีละรายการจะกลายเป็น 25 ล้าน request ต่อวัน โดยไม่จำเป็น

## 2026-09-12 · เก็บ vn/an ได้ แต่ hn ต้อง hash

**ตัดสินใจ:** เก็บ `vn`, `an` ตรง ๆ · `hn` เก็บเป็น hash เท่านั้น

**ทำไม:** vn กับ an เป็นเลขอ้างอิงภายในของโรงพยาบาล เปิดดูเฉย ๆ ไม่รู้ว่าใคร
แต่ hn เป็นเลขประจำตัวผู้ป่วยที่ผูกทุก visit ของคนเดียวกัน
เก็บ hn ดิบ = ระบบนี้กลายเป็นระบบข้อมูลส่วนบุคคลตาม PDPA
ซึ่งขัดกับข้อกำหนดของโปรเจกต์เอง

เก็บเป็น hash ยังตอบได้ว่า "คนไข้รายเดิมมีปัญหาซ้ำกี่ครั้ง" โดยไม่รู้ว่าเป็นใคร

**ยังไม่สรุป:** เจ้าของงานยังไม่ยืนยันข้อนี้ ต้องถามก่อนลงมือ Phase 2

## 2026-09-12 · เขียนปฏิทินเอง ไม่ใช้ไลบรารี

**ตัดสินใจ:** เขียน `DateRangePicker` เองใน `components/ui/date-range-picker.tsx`

**ทำไม:** ปฏิทินไทยต้องแสดงปี พ.ศ. และชื่อเดือนไทย
ไลบรารีปฏิทินส่วนใหญ่ทำมาเพื่อ ค.ศ. ถ้าจะดัดให้เป็น พ.ศ. ต้องเขียน adapter
ครอบทุกจุดที่แสดงปี ซึ่งโค้ดพอ ๆ กับเขียนเองแต่ควบคุมยากกว่า
และได้ dependency เพิ่มมาโดยไม่จำเป็น

ปฏิทินตัวนี้ใช้แค่ grid กับการเทียบวันที่ ไม่ได้ซับซ้อน

**ไม่เอา:** react-day-picker หรือ MUI DatePicker (ต้องดัดเรื่อง พ.ศ. อยู่ดี)

## 2026-09-12 · เลือกช่วงวันที่ได้แบบปุ่มลัดคู่กับปฏิทิน

**ตัดสินใจ:** มีปุ่มลัด 6 ตัว (วันนี้ เมื่อวาน 7 วัน 30 วัน เดือนนี้ เดือนก่อน)
และปุ่มกำหนดเองที่เปิดปฏิทินเลือกช่วงอิสระ

**ทำไม:** ผู้ใช้ 2 กลุ่มมีพฤติกรรมต่างกัน
ผู้บริหารเปิดดูภาพรวมประจำ กดปุ่มลัดจบใน 1 คลิก
ส่วน PM กับทีมฝึกอบรมต้องเจาะช่วงเฉพาะ เช่น สัปดาห์ที่ไปอบรม จึงต้องมีปฏิทิน

ถ้ามีแค่ปฏิทินอย่างเดียว คนที่แค่อยากดู 7 วันต้องกดหลายครั้งทุกวัน

**ไม่จำกัดย้อนหลัง** ตามที่เจ้าของงานระบุ เลือกย้อนได้เท่าที่มีข้อมูล
⚠️ Phase 2 ต้องระวัง ถ้าเลือกช่วงกว้างมาก (เช่น 2 ปี) query จะช้า
ต้องมี pre-aggregate รายวันไว้ล่วงหน้า ไม่ใช่ scan ตารางดิบทุกครั้ง

## 2026-09-12 · ห้ามใช้ toISOString แปลงวันที่

**ตัดสินใจ:** ใช้ `toApiDate()` ที่ประกอบ string จากเวลาท้องถิ่น

**ทำไม:** `toISOString()` แปลงเป็น UTC ประเทศไทยเป็น UTC+7
วันที่ 12 ก.ย. เวลา 00:30 น. จะกลายเป็น 11 ก.ย. ใน UTC
**ยอดของวันจะเพี้ยนไป 1 วันโดยไม่มี error ให้เห็น** ซึ่งอันตรายมากกับระบบการเงิน

บั๊กแบบนี้จับยากเพราะจะเห็นเฉพาะช่วงเวลาก่อน 07:00 น. เท่านั้น

## 2026-09-12 · ใช้ทะเบียนหน่วยบริการจริงจากกระทรวง แทนข้อมูลที่ตั้งเอง

**ตัดสินใจ:** ประเภทหน่วยบริการ จังหวัด เขตสุขภาพ และชื่อหน่วยบริการ
ใช้ทะเบียนจริงจาก hcode.moph.go.th ทั้งหมด ไม่ตั้งเอง

**ที่มา:** ไฟล์ health_office.csv ดึงเมื่อ 12 ก.ย. 2569 มี 44,374 แห่ง
กำลังใช้งาน 42,984 แห่ง generate เป็น `src/mocks/moph-registry.ts`
ด้วยสคริปต์ ห้ามแก้ไฟล์นั้นด้วยมือ

**สิ่งที่เปลี่ยน:**

- ประเภทหน่วยบริการจาก 10 ประเภทที่ตั้งเอง เป็น 17 ประเภทตามทะเบียนจริง
  ของเดิมมี "ร้านยา" ซึ่งไม่มีในทะเบียนประเภทหน่วยบริการสุขภาพ
  และไม่มี "สสอ." กับ "สสจ." ซึ่งมีจริงรวมกัน 954 แห่ง
- จังหวัดจาก 48 เป็น 77 จังหวัดครบ ผูกเขตสุขภาพตามจริง
  (ยืนยันแล้วว่าแต่ละจังหวัดอยู่เขตเดียว ไม่มีจังหวัดคาบเกี่ยว)
- ชื่อหน่วยบริการใช้ชื่อจริง ไม่ได้ประกอบจาก pattern
  เพราะชื่อจริงหลากหลายกว่ามาก เช่น "โรงพยาบาลเชียงรายประชานุเคราะห์"
  ไม่ใช่ "โรงพยาบาลเชียงราย" ตาม pattern ที่เคยเขียนไว้

**รหัสหน่วยบริการมี 3 แบบ ไม่ใช่แบบเดียว**

หน่วยที่ขอรหัสตั้งแต่ 1 เม.ย. 2568 ได้เฉพาะรหัส 9 หลักใหม่ (`CA0032045`)
ในทะเบียนมี 3,155 แห่งที่ไม่มีรหัสเก่าเลย เป็นคลินิกเอกชน 3,049 แห่ง
`Provider` จึงเก็บครบทั้ง 3 ช่อง และมี `matchesCode()` ให้จับคู่ได้ทุกแบบ

**ทางเลือกที่ไม่เอา:** เก็บรหัสช่องเดียวแล้วแปลงเอา
ตรวจแล้วพบว่ารหัส 9 หลักเดิมกับ 5 หลักไม่ได้แปลงกันตรง ๆ ทุกแถว
มี 469 แถวที่ไม่เข้าสูตร (ส่วนใหญ่เป็นหน่วยสาขา) ถ้าแปลงเอาจะ map ผิดเงียบ ๆ

**เก็บ `district` ไว้ในทะเบียนแม้ยังไม่ได้ใช้** เพราะทะเบียนมี 923 อำเภอ
ถ้าผู้บริหารขอดูรายอำเภอภายหลังจะได้ไม่ต้องดึง CSV ใหม่
