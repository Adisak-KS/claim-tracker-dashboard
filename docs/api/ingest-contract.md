# รูปแบบข้อมูลที่ระบบต้นทางยิงเข้ามา

> **สถานะ: ร่าง ยังไม่ได้ใช้จริง** Phase 2 ค่อยลงมือ
> เอกสารนี้ออกแบบจากการอ่านโค้ดส่งเคลมจริง ไม่ได้เดาเอา

## ที่มาของการออกแบบ

อ่านโค้ดฝั่ง HOSxP (`cxButton10Click` ใน `HOSxPNHSOEclaimFeeScheduleRegisterFormUnit.pas`)
แล้วพบพฤติกรรมจริง 4 อย่างที่กำหนดรูปแบบ API

| พฤติกรรมของโปรแกรมส่งเคลม | ผลกับ API ของเรา |
|---|---|
| `SignOn` ครั้งเดียวต่อ batch แล้วส่งเป็นชุด | รับเป็น batch ไม่ใช่ทีละรายการ |
| ส่งเป็น chunk ละ 10 ราย (ข้อจำกัด สปสช.) | ต้องรองรับหลาย chunk ต่อ 1 batch |
| chunk ที่ fail นับเป็น error แล้ว **ส่งใหม่ได้** | ฝั่งเราต้องกันนับซ้ำเอง |
| เก็บแค่ `vn` กับ `hn` ต่อรายการ | `vn` เป็น key ธรรมชาติอยู่แล้ว |

## 🔴 เส้นเดียวจบ ฝั่งเราแยกเองว่าใหม่หรือซ้ำ

**ระบบต้นทางมี endpoint เดียว** ไม่ว่าจะเป็นส่งครั้งแรก ส่งซ้ำหลังแก้ข้อมูล
ผลจากการกดตรวจสอบสถานะ หรือการยกเลิก ยิงมาที่เส้นนี้เส้นเดียวหมด

เหตุผล: ฝั่ง รพ. ไม่ควรต้องรู้ว่าข้อมูลที่ส่งมาเป็นของใหม่หรือของเดิม
เขารู้แค่ว่า "ตอนนี้รายการนี้มีสถานะแบบนี้" แล้วส่งมา ที่เหลือเป็นงานของเรา

ถ้าให้เขาเลือก endpoint เอง จะมีวันที่เลือกผิด แล้วข้อมูลจะเพี้ยนแบบไม่มีใครรู้

### กุญแจธรรมชาติ 3 ส่วน

```
(hospitalCode, sourceSystem, vn)
```

ทั้ง 3 ค่ามาในทุก request อยู่แล้ว ไม่ต้องขออะไรเพิ่มจากระบบต้นทาง

🔴 **ต้องมี `sourceSystem` ในกุญแจด้วย ห้ามใช้แค่ (hospitalCode, vn)**
เพราะ รพ. แห่งเดียวอาจใช้หลายระบบพร้อมกัน และ VN เป็นเลขที่แต่ละระบบออกเอง
`HOSxP` กับ `EHP` ในโรงพยาบาลเดียวกันจึงออก VN ซ้ำกันได้
ถ้าไม่แยกระบบ ข้อมูลของสองระบบจะทับกันเงียบ ๆ

(เหตุผลเดียวกับที่ VN ซ้ำข้ามโรงพยาบาลได้ ดู [decisions](../design/decisions.md))

### ตัดสินใจยังไงว่าใหม่หรือซ้ำ

| เจอในฐานข้อมูล | ข้อมูลที่ส่งมา | ทำอะไร |
|---|---|---|
| ไม่เจอ | อะไรก็ได้ | เพิ่มรายการใหม่ |
| เจอ | **เหมือนเดิมทั้งก้อน** | ไม่ทำอะไร ไม่นับซ้ำ |
| เจอ | มีอะไรเปลี่ยน | เพิ่มประวัติใหม่ แล้วเลื่อนสถานะปัจจุบันมาที่ค่าใหม่ |

ข้อกลางคือตัวกันยอดพอง โรงพยาบาลที่ยิงซ้ำ 3 รอบเพราะเน็ตหลุด
จะไม่ทำให้ยอดตัวเองพอง 3 เท่า เพราะเนื้อข้อมูลเหมือนเดิม

### 🔴 "เปลี่ยน" ต้องเทียบ errors ด้วย ไม่ใช่เทียบแค่ status

ต้องเทียบให้ครบทุกอย่างนี้ ต่างแม้แต่อย่างเดียวถือว่าเปลี่ยน

| เทียบอะไร | ทำไมต้องเทียบ |
|---|---|
| `status` | สถานะหลักเปลี่ยน เช่น รอตรวจเป็นจ่ายแล้ว |
| **`errors[]` ทั้งชุด** | รหัสปัญหาเปลี่ยนได้โดย status เท่าเดิม |
| `cancelled` | ยกเลิกแล้วส่งใหม่ ต้องเห็นทั้งสองเหตุการณ์ |
| `nhsoUid` | ได้ uid มาทีหลังจากการตรวจสอบสถานะ |

**เคสที่พังถ้าเทียบแค่ `status`:** รายการหนึ่งติด `C001` วันนี้
พรุ่งนี้หน่วยบริการแก้แล้วส่งใหม่ ยังไม่ผ่าน แต่คราวนี้ติด `G01` แทน
`status` ยังเป็น `1101` เท่าเดิมทั้งคู่ ถ้าเทียบแค่ status จะตัดสินว่า "เหมือนเดิม"
แล้วหน้าจอจะค้างแสดง `C001` ตลอดไป ทั้งที่ปัญหาจริงเปลี่ยนไปแล้ว

ผลคือเจ้าหน้าที่โทรไปบอกหน่วยบริการให้แก้เรื่องที่แก้ไปแล้ว
และรหัสที่ติดอยู่จริงจะไม่ถูกนับในหน้าจัดอันดับปัญหาเลย

**เทียบ `errors[]` ต้องไม่สนลำดับ** สปสช. ไม่รับประกันว่าจะส่งมาเรียงเหมือนเดิม
ให้เรียงรหัสก่อนเทียบ ไม่งั้นข้อมูลชุดเดิมที่สลับลำดับจะถูกนับเป็นการเปลี่ยนแปลง
แล้วประวัติจะพองด้วยแถวที่ไม่มีอะไรต่างกัน

### เก็บประวัติทุกครั้งที่เปลี่ยน ไม่ทับของเดิม

ทีมฝึกอบรมต้องดูได้ว่าหน่วยบริการไหนแก้ปัญหาเดิมวนซ้ำกี่รอบ
และดูได้ว่ารายการหนึ่งเคยติดอะไรมาบ้างก่อนจะผ่าน ถ้าทับ ข้อมูลนั้นหายถาวร

ยอดบนแดชบอร์ดนับจากสถานะปัจจุบันของแต่ละรายการเท่านั้น ไม่ได้นับทุกแถวประวัติ
รวมถึงหน้าจัดอันดับปัญหาด้วย ไม่งั้นรหัสที่แก้ไปแล้วจะยังค้างอยู่ในอันดับ

## รูปแบบที่เสนอ

### ส่งข้อมูลเข้ามา

```
POST /api/v1/claim-batches
```

**Header**

| ชื่อ | จำเป็น | ความหมาย |
|---|---|---|
| `X-API-Key` | ใช่ | key ประจำโรงพยาบาล |
| `Content-Encoding: gzip` | ใช่ | บังคับบีบอัด payload (ดูหัวข้อขนาด payload) |

ไม่มี `Idempotency-Key` เพราะกันซ้ำด้วยกุญแจธรรมชาติแทน (ดูหัวข้อข้างบน)
ฝั่ง รพ. จึงไม่ต้องเก็บหรือสร้าง key อะไรเลย ยิงมาได้ตลอด

**Body**

```json
{
  "hospitalCode": "CA0032045",
  "scheme": "nhso-13f",
  "sourceSystem": "HOSxP",
  "sourceVersion": "3.68.2.14",
  "fund": "NHSO",
  "batchRef": "20260912-001",
  "submittedAt": "2026-09-12T09:15:00+07:00",
  "summary": {
    "total": 1250,
    "success": 1180,
    "failed": 63,
    "skipped": 7
  },
  "items": [
    {
      "vn": "680912001234",
      "an": null,
      "status": "1103",
      "nhsoUid": "bf680fd4-2c1a-4e3b-9a77-1234567890ab",
      "errors": []
    },
    {
      "vn": "680912001235",
      "status": "1101",
      "nhsoUid": null,
      "errors": [
        { "code": "C001", "field": "charge_code", "allowClaim": "N" }
      ]
    }
  ]
}
```

### ส่งผลตรวจสอบสถานะกับการยกเลิกมาเส้นเดียวกัน

ใช้ body หน้าตาเดิมทุกอย่าง เปลี่ยนแค่ค่าใน `status` และเพิ่ม `cancelled` เมื่อยกเลิก
ระบบจับคู่กับรายการเดิมด้วย (hospitalCode, sourceSystem, vn) แล้วเลื่อนสถานะให้เอง

```json
{
  "hospitalCode": "CA0032045",
  "scheme": "nhso-13f",
  "sourceSystem": "HOSxP",
  "batchRef": "20260913-status",
  "submittedAt": "2026-09-13T10:00:00+07:00",
  "summary": { "total": 2, "success": 1, "failed": 0, "skipped": 0 },
  "items": [
    {
      "vn": "680912001235",
      "status": "5005",
      "nhsoUid": "bf680fd4-2c1a-4e3b-9a77-1234567890ab",
      "errors": []
    },
    {
      "vn": "680912001234",
      "status": "1103",
      "cancelled": true,
      "errors": []
    }
  ]
}
```

ค่าที่ สปสช. คืนจาก `status-tracks` แมปเข้ามาตรงนี้: `statusCode` เข้า `status`
`uid` เข้า `nhsoUid` ส่วน `message` กับ `statusDesc` ใส่ใน `errors[].message` ได้ถ้ามี

### ข้อกำหนดของแต่ละ field

| field | กติกา |
|---|---|
| `scheme` | ประเภทการส่งเคลม ต้องส่งมาเสมอ ห้ามปล่อยว่าง (ดูหัวข้อถัดไป) |
| `hospitalCode` | รหัสหน่วยบริการ ยาวไม่เกิน 9 ตัว ต้องตรงกับเจ้าของ API key (ดูหัวข้อถัดไป) |
| `status` | ต้องเป็นรหัสสถานะจริงของ สปสช. (ดู [nhso-status-codes](../domain/nhso-status-codes.md)) |
| `errors[].code` | ต้องเป็นรหัสข้อผิดพลาดจริง (ดู [nhso-error-codes](../domain/nhso-error-codes.md)) |
| `errors[].allowClaim` | `Y` หรือ `N` ตามที่ สปสช. กำหนดต่อรหัสนั้น |
| `sourceSystem` | ต้องส่งมาเสมอ เป็นส่วนหนึ่งของกุญแจ ค่าที่รับ: `HOSxP` `EHP` `NHIP` `OTHER` |
| `cancelled` | ใส่ `true` เมื่อยกเลิกรายการ ไม่ใส่ = ไม่ใช่การยกเลิก |
| `items` | **1 รายการขึ้นไป** ส่งทีละ 1 ก็ได้ ส่งทั้งชุด 10 ก็ได้ (เพดาน 100 รายการและ 20 MB กันไว้อีกชั้น) |

## 🔴 ระบบต้นทางส่งได้ไม่เท่ากัน ต้องรับของน้อยได้

ระบบต้นทางแต่ละเจ้าเก็บข้อมูลไม่เหมือนกัน และบางแห่งมีนโยบายไม่ส่งบางอย่างออกมา
(โดยเฉพาะยอดเงิน ซึ่งบางแห่งถือว่าเป็นข้อมูลภายใน)

🔴 **ห้ามบังคับให้ส่งครบทุก field** ถ้าบังคับแล้วเขาส่งไม่ได้
เราจะไม่เห็นหน่วยบริการนั้นในระบบเลย ซึ่งแย่กว่าการเห็นแบบข้อมูลไม่ครบ
หน่วยที่หายไปทั้งหน่วยคือหน่วยที่ไม่มีใครรู้ว่ามีปัญหา

### แบ่งเป็น 3 ชั้น

| ชั้น | field | ถ้าไม่ส่ง |
|---|---|---|
| **บังคับ** | `hospitalCode` `scheme` `sourceSystem` `items[].vn` `items[].hnHash` `items[].status` | ปฏิเสธทั้ง batch |
| **แนะนำ** | `errors[]` `submittedAt` `sourceVersion` `nhsoUid` | รับได้ แต่หน้าจอจะบอกไม่ได้ว่าติดอะไร |
| **ถ้ามี** | ยอดเงิน `claimType` `claimItems[]` `seq` `an` | รับได้ ซ่อนส่วนที่เกี่ยวข้องบนหน้าจอ |

ชั้นบังคับมีแค่ 6 ตัว เพราะเป็นขั้นต่ำที่ตอบคำถาม "ใครส่ง ส่งอะไร ผลเป็นไง" ได้
น้อยกว่านี้ไม่มีความหมายพอจะขึ้นหน้าจอ

🔴 **`hnHash` บังคับ แต่ต้องเป็นค่า hash ไม่ใช่ hn ดิบ** ถ้าส่ง hn ดิบมาให้ปฏิเสธทั้ง batch
เหตุผลอยู่ในหัวข้อ `hn` ต้อง hash ก่อนส่ง ด้านล่าง

### 🔴 ไม่ส่ง ไม่เท่ากับ เป็นศูนย์

ต้องแยก 2 อย่างนี้ให้ขาดในฐานข้อมูล ห้ามยุบเป็นค่าเดียวกัน

| ความหมาย | เก็บเป็น | หน้าจอแสดง |
|---|---|---|
| ระบบต้นทางไม่ได้ส่งมา | `null` | `ไม่มีข้อมูล` |
| ส่งมาแล้วและค่าคือศูนย์ | `0` | `0 บาท` |

ถ้ายุบเป็น 0 ทั้งคู่ หน่วยบริการที่ไม่ส่งยอดเงินจะกลายเป็น "เบิกได้ 0 บาท"
แล้วค่าเฉลี่ยทั้งเขตจะเพี้ยนโดยไม่มีใครรู้ ผู้บริหารจะเห็นตัวเลขที่ต่ำกว่าความจริง

**ห้ามเอา field ที่เป็น null ไปหาค่าเฉลี่ยหรือผลรวม** ให้ตัดออกจากการคำนวณ
แล้วบอกบนหน้าจอด้วยว่าคิดจากกี่หน่วยจากทั้งหมดกี่หน่วย

### หน้าจอต้องบอกว่าข้อมูลไม่ครบ

ห้ามแสดงช่องว่างเฉย ๆ เพราะผู้ใช้จะคิดว่าระบบพัง
ให้บอกตรง ๆ ว่า "ระบบต้นทางไม่ได้ส่งข้อมูลส่วนนี้มา" พร้อมชื่อระบบ
ทีมที่ดูแลจะได้รู้ว่าต้องไปคุยกับใครถ้าอยากได้ข้อมูลเพิ่ม

## 🔴 `scheme` ต้องระบุมาเสมอ ห้ามเดาแทน

ระบบรองรับการส่งเคลมได้หลายประเภท แต่ละประเภทมีรหัสสถานะและรหัสข้อผิดพลาดคนละชุด

| ค่า | หมายถึง |
|---|---|
| `nhso-13f` | 13 แฟ้ม ส่ง สปสช. |

ตอนนี้มีประเภทเดียว แต่ **ถ้าไม่ส่ง `scheme` มาต้องปฏิเสธทั้ง batch**
ห้ามเติมให้เป็น `nhso-13f` อัตโนมัติ

เหตุผล: รหัส `C001` ของ สปสช. กับรหัสชื่อเดียวกันของหน่วยงานอื่นคนละความหมาย
ถ้าเดาผิดจะถูกนับรวมเป็นปัญหาเดียวกัน ตัวเลขบนแดชบอร์ดผิดแบบเงียบ ๆ ไม่มี error ให้เห็น
เหมือนกรณีกุญแจธรรมชาติข้างบน คือแก้ทีหลังไม่ได้เพราะข้อมูลปนกันไปแล้ว

## 🔴 `hospitalCode` มี 3 แบบ ห้ามตรึงรูปแบบ

กระทรวงสาธารณสุขออกรหัสให้หน่วยบริการ 3 แบบ
(ยืนยันจากทะเบียน hcode.moph.go.th ดึงเมื่อ 12 ก.ย. 2569 มี 44,374 แห่ง)

| แบบ | ตัวอย่าง | หมายเหตุ |
|---|---|---|
| รหัส 9 หลักใหม่ | `CA0032045` | ตัวอักษร 2 ตัว + เลข 7 หลัก **มีครบทุกแห่ง** |
| รหัส 9 หลักเดิม | `003204500` | ตัวเลขล้วน หน่วยที่ขึ้นทะเบียนใหม่ไม่มี |
| รหัส 5 หลักเดิม | `32045` | หน่วยที่ขึ้นทะเบียนใหม่ไม่มี |

**หน่วยที่ขอรหัสตั้งแต่ 1 เม.ย. 2568 เป็นต้นไป ได้เฉพาะรหัส 9 หลักใหม่**
ในทะเบียนมี 3,155 แห่งที่ไม่มีรหัสเก่าเลย เป็นคลินิกเอกชน 3,049 แห่ง
ถ้าระบบตรึงรหัส 5 หลัก หน่วยกลุ่มนี้จะส่งเข้าไม่ได้ทั้งกลุ่ม

ตัวอักษรนำหน้าผูกกับประเภทหน่วยงาน: `CA` คลินิกเอกชน · `GA` รพ.สต. และ อปท. ·
`EA` รพ.ชุมชน · `BA` สสอ. · `HA` รพ.เอกชน · `IA` ศูนย์วิชาการ · `FA` รพ.นอก สธ. ·
`AA` สสจ. · `CB` คลินิกเอกชน (ตัวสำรองเมื่อ `CA` ใกล้เต็ม)

🔴 **ห้ามเขียน regex ตรึงรายการตัวอักษรนี้** เพราะกระทรวงเพิ่มตัวใหม่เรื่อย ๆ
(`CB` มีแค่ 3 แห่ง คือตัวที่เพิ่งเริ่มใช้) ถ้าตรึงไว้แล้วเขาออกตัวใหม่
ระบบเราจะปฏิเสธข้อมูลจริงทิ้งโดยไม่มีใครรู้

ให้ตรวจแค่ 2 อย่าง: ยาวไม่เกิน 9 ตัว และ **มีรหัสนี้อยู่ในทะเบียนที่เราซิงก์มาหรือไม่**
ไม่ใช่ตรวจว่าหน้าตาถูก format

หน่วยเดียวกันอาจส่งคนละรหัสมาคนละครั้ง (ระบบเก่าส่ง 5 หลัก ระบบใหม่ส่ง 9 หลักใหม่)
ระบบจึงต้องเก็บครบทั้ง 3 ช่องแล้วจับคู่ได้ทุกแบบ ไม่งั้นหน่วยเดียวจะถูกนับเป็น 2 แห่ง

### ขนาด payload: ส่งทีละ 1 หรือทีละหลายรายการก็ได้

**`items` รับตั้งแต่ 1 รายการขึ้นไป** ระบบต้นทางเลือกได้เองว่าจะส่งแบบไหน

| กรณี | ส่งอย่างไร |
|---|---|
| กดส่งรายการเดียว (เมนูคลิกขวา) | `items` มี 1 รายการ |
| ส่งทั้งชุดตามรอบ สปสช. | `items` มี 10 รายการ |
| อยากรวบหลายรอบส่งทีเดียว | `items` มีถึง 100 รายการ |

**แนะนำให้ส่งเป็นชุดตามรอบที่ส่ง สปสช. อยู่แล้ว** เพราะไม่ต้องแก้อะไรเลย
และลดจำนวน request ลง 10 เท่าเมื่อเทียบกับส่งทีละรายการ
แต่ไม่ได้บังคับ ส่งทีละ 1 ก็ทำงานได้ปกติ

โปรแกรมส่งเคลมแบ่งเป็นชุดละ 10 รายการอยู่แล้วตามข้อจำกัดของ สปสช.
(ยืนยันจากโค้ด `FChunkSize := 10` ใน HOSxPNHSOEClaimFreeScheduleSendThread.pas)
พอส่ง สปสช. ครบชุดหนึ่งแล้วได้ผลกลับมา ก็ส่งผลชุดนั้นต่อมาหาเราได้ทันที
ไม่ต้องนับใหม่ ไม่ต้องรวมชุด ไม่ต้องคำนวณขนาด

ขนาดที่ได้จากการส่งทีละ 10 รายการ (แบบที่แนะนำ)

| เคส | บรรทัดต่อรายการ | 10 รายการ (ดิบ) | บนสายหลัง gzip | ส่งได้สูงสุด |
|---|---|---|---|---|
| ผู้ป่วยนอกทั่วไป | 20 | 0.03 MB | 0.004 MB | 100 ราย |
| ผู้ป่วยในทั่วไป | 300 | 0.36 MB | 0.05 MB | 100 ราย |
| ผู้ป่วยในรายหนัก | 1,000 | 1.20 MB | 0.16 MB | 100 ราย |
| ผู้ป่วยหนักนอนนาน | 3,000 | 3.54 MB | 0.48 MB | 57 ราย |
| ผู้ป่วยหนักนอนนาน 2 เดือน | 6,000 | 7.07 MB | 0.95 MB | 28 ราย |

🔴 **ผู้ป่วยในคือเคสที่ต้องเผื่อ ไม่ใช่ผู้ป่วยนอก** เพราะ `claimItems[]` เป็นรายบรรทัด
ค่ารักษา ผู้ป่วยนอนนานจึงมีได้หลายพันบรรทัดต่อรายการ ต่างจากผู้ป่วยนอกหลายร้อยเท่า

**ทุกเคสส่งเต็มชุด 10 รายการได้สบาย** สองแถวล่างจำกัดที่ 28-57 ราย
แต่ยังมากกว่ารอบจริงที่ส่งทีละ 10 อยู่หลายเท่า จึงไม่มีกรณีที่ส่งตามปกติแล้วถูกปฏิเสธ

**เพดาน 100 รายการและ 20 MB เป็นตาข่ายกันเครื่องล่ม** ไม่ใช่กฎที่ต้องคำนวณตาม

🔴 **ห้ามรับ payload ขนาดไม่จำกัด** เพราะต้องอ่านเข้าหน่วยความจำก่อนถึงจะแยกได้
ถ้าหลายพันหน่วยส่งก้อนใหญ่พร้อมกัน เครื่องจะล่มก่อนได้เริ่มแยก
และหน่วยที่ส่งก้อนใหญ่จะทำให้หน่วยอื่นที่ไม่ได้ทำอะไรผิดใช้งานไม่ได้ไปด้วย

### 🔴 ระบบเราล่มต้องไม่ทำให้หน่วยบริการส่งเคลมไม่ได้

**นี่คือข้อกำหนดที่สำคัญที่สุดในเอกสารนี้**

ระบบนี้เป็นแค่ตัวติดตามสถานะ ไม่ใช่ทางผ่านของการส่งเคลม
หน่วยบริการส่งเคลมไปที่ สปสช. โดยตรงอยู่แล้ว การส่งข้อมูลมาหาเรา
เป็นงานรองที่เกิดขึ้นหลังจากได้ผลจาก สปสช. แล้ว

ถ้าระบบเราล่ม ช้า หรือเน็ตขาด **การส่งเคลมของหน่วยบริการต้องทำงานต่อได้ตามปกติ**

กติกาที่ฝั่งระบบต้นทางต้องทำ

| ข้อ | ทำอะไร |
|---|---|
| ยิงแบบไม่รอผล | ส่งข้อมูลมาหาเราในเธรดแยก ห้ามให้หน้าจอผู้ใช้รอ |
| ตั้ง timeout สั้น | 5-10 วินาทีพอ เกินแล้วเลิกรอ อย่าค้าง |
| ล้มเหลวแล้วไปต่อ | ห้ามขึ้น error ขวางผู้ใช้ ห้ามหยุดการส่งเคลมรอบถัดไป |
| เก็บไว้ส่งทีหลัง | ใส่คิวในเครื่องตัวเอง แล้วลองใหม่เมื่อระบบกลับมา |

🔴 **ห้ามให้การส่งข้อมูลมาหาเราอยู่ในเส้นทางเดียวกับการส่งเคลม**
ถ้าเขียนโค้ดให้ "ส่ง สปสช. เสร็จแล้วส่งมาหาเรา ถ้าพลาดให้ throw"
วันที่ระบบเราล่มจะกลายเป็นวันที่ทั้งประเทศส่งเคลมไม่ได้

เหตุผลฝั่งเรา: ระบบเราตอบ 202 แล้วเข้าคิว จึงตอบเร็วมากอยู่แล้ว
แต่ต่อให้เร็วแค่ไหน เครื่องก็ล่มได้ และวันนั้นต้องไม่มีใครเดือดร้อน

**เราต้องออกแบบให้ข้อมูลที่ค้างส่งไม่หาย** ข้อมูลที่ส่งมาช้าไป 3 วันยังมีค่า
เพราะกุญแจธรรมชาติทำให้ส่งซ้ำได้โดยไม่นับซ้ำ (ดูหัวข้อข้างบน)
หน่วยบริการจึงส่งย้อนหลังได้เสมอโดยไม่ต้องกลัวข้อมูลเพี้ยน

### 🔴 บังคับบีบอัดด้วย gzip

ส่ง `Content-Encoding: gzip` เสมอ JSON ชุดนี้มีคำซ้ำเยอะ
วัดจากข้อมูลจริงแล้วบีบเหลือประมาณ 13% ของขนาดเดิม
เคสหนักที่สุด (ผู้ป่วยหนัก 2 เดือน 10 ราย) จึงส่งบนสายจริงไม่ถึง 1 MB

🔴 **เพดาน 20 MB นับจากขนาดหลังคลายบีบอัด ไม่ใช่ขนาดที่ส่งมาบนสาย**
ถ้านับจากขนาดบนสาย จะเปิดช่องให้ส่งไฟล์บีบอัดเล็ก ๆ ที่คลายออกมาเป็นหลาย GB
ซึ่งกว่าจะรู้ก็คลายไปแล้วและหน่วยความจำหมดไปแล้ว

ต้องหยุดคลายทันทีที่เกินเพดาน ห้ามคลายจนจบแล้วค่อยเช็คขนาด

20 MB เป็นขนาดที่เครื่องเราถือไว้ตอนแกะ ไม่ใช่ปริมาณที่วิ่งบนเน็ต
ซึ่งจริง ๆ แล้วไม่ถึง 3 MB

### 🔴 ห้ามส่งเข้ามาเด็ดขาด

ชื่อ นามสกุล เลขบัตรประชาชน ที่อยู่ เบอร์โทร วันเกิด
รหัสวินิจฉัยรายบุคคล ผลตรวจ รายการยา

ถ้าเจอ field พวกนี้ **ระบบต้องปฏิเสธทั้ง batch** ไม่ใช่รับแล้วค่อยกรอง
เพราะรับเข้ามาแล้วถือว่าเก็บแล้ว

### `hn` ต้อง hash ก่อนส่ง

ถ้าจำเป็นต้องส่ง ให้ hash ที่ฝั่ง รพ. ก่อน พร้อม salt ประจำโรงพยาบาล
ห้ามส่ง hn ดิบเข้ามา (ดูเหตุผลใน [decisions](../design/decisions.md))

## ตอบกลับ

**รับเรื่องแล้ว (202)**

```json
{
  "batchId": "01JBXZ9K2M4N5P6Q7R8S9T0V1W",
  "received": 1250,
  "duplicate": false
}
```

ตอบ 202 ไม่ใช่ 200 เพราะระบบรับเข้าคิวแล้วประมวลผลทีหลัง
ตอบเร็วทำให้ รพ. ไม่ต้องรอ และรองรับการยิงพร้อมกันได้มากขึ้น

**ส่งข้อมูลที่เคยส่งแล้ว (202 เหมือนกัน)**

```json
{
  "batchId": "01JBXZ9K2M4N5P6Q7R8S9T0V1X",
  "received": 1250,
  "created": 120,
  "updated": 45,
  "unchanged": 1085
}
```

ตอบสำเร็จเหมือนเดิมเสมอ ฝั่ง รพ. ไม่ต้องเขียนโค้ดพิเศษและไม่ต้องสนใจตัวเลขนี้
แต่เก็บไว้ให้เราตรวจสอบได้ว่าที่ยิงมาเป็นของใหม่จริงเท่าไร

`unchanged` สูงผิดปกติแปลว่าระบบต้นทางยิงข้อมูลเดิมซ้ำโดยไม่จำเป็น

**ส่งเกินเพดาน (413)**

```json
{
  "error": "PAYLOAD_TOO_LARGE",
  "message": "ข้อมูลชุดนี้ใหญ่เกินกำหนด กรุณาแบ่งส่งเป็นชุดย่อย",
  "limit": { "maxItems": 100, "maxBytes": 20971520 },
  "received": { "items": 100, "bytes": 27262976 },
  "suggestedItems": 80
}
```

ต้องบอก `suggestedItems` มาด้วยเสมอ เพื่อให้ฝั่งต้นทางแบ่งใหม่ได้ทันที
โดยไม่ต้องลองผิดลองถูก คำนวณจากขนาดจริงที่ได้รับเทียบกับเพดาน

**ข้อมูลผิดรูปแบบ (400)**

```json
{
  "error": "INVALID_PAYLOAD",
  "message": "พบข้อมูลส่วนบุคคลใน field ที่ไม่อนุญาต",
  "details": [{ "path": "items[3].patientName", "reason": "FORBIDDEN_FIELD" }]
}
```

## รองรับโหลด 5,000+ โรงพยาบาล

| ปัญหา | วิธีรับมือ |
|---|---|
| ยิงพร้อมกันตอนสิ้นเดือน | รับเข้าคิว (BullMQ) แล้วตอบ 202 ทันที |
| รพ. เดียวยิงถี่มาก | จำกัดอัตราต่อ API key |
| ข้อมูลซ้ำ | เทียบกุญแจธรรมชาติ (hospitalCode, sourceSystem, vn) |
| เขียนลงฐานข้อมูลไม่ทัน | เขียนเป็นชุดผ่าน worker ไม่เขียนทีละแถว |

## ยังไม่สรุป

- BMS Life ออก API key ให้ รพ. ยังไง หรือเราออกเอง
- เก็บข้อมูลย้อนหลังกี่ปี
- เก็บประวัติการเปลี่ยนสถานะย้อนหลังกี่ชั้นต่อ 1 รายการ
