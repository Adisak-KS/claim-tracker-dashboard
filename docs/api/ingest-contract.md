# รูปแบบข้อมูลที่ระบบต้นทางยิงเข้ามา

> **สถานะ: ร่าง ยังไม่ได้ใช้จริง** Phase 2 ค่อยลงมือ
> เอกสารนี้ออกแบบจากการอ่านโค้ดส่งเคลมจริง ไม่ได้เดาเอา

## ที่มาของการออกแบบ

อ่านโค้ดฝั่ง HOSxP (`cxButton10Click` ใน `HOSxPNHSOEclaimFeeScheduleRegisterFormUnit.pas`)
แล้วพบพฤติกรรมจริง 4 อย่างที่กำหนดรูปแบบ API

| พฤติกรรมของโปรแกรมส่งเคลม | ผลกับ API ของเรา |
|---|---|
| `SignOn` ครั้งเดียวต่อ batch แล้วส่งเป็นชุด | รับเป็น batch ไม่ใช่ทีละรายการ |
| ส่งเป็น chunk ละ 10 ราย (ข้อจำกัด สปสช.) | ต้องรองรับหลาย chunk ต่อ 1 batch |
| chunk ที่ fail นับเป็น error แล้ว **ส่งใหม่ได้** | ต้องมี idempotency key กันนับซ้ำ |
| เก็บแค่ `vn` กับ `hn` ต่อรายการ | `vn` เป็น key ธรรมชาติอยู่แล้ว |

## 🔴 idempotency key คือหัวใจ

โปรแกรมส่งเคลมออกแบบให้ส่งซ้ำได้เมื่อ fail ซึ่งถูกต้องในมุมของ รพ.
แต่ถ้าฝั่งเราไม่มีอะไรกัน โรงพยาบาลที่ลองส่งซ้ำ 3 รอบจะทำให้ยอดตัวเองพอง 3 เท่า

พอตัวเลขพองแล้ว **แดชบอร์ดทั้งระบบเชื่อถือไม่ได้** ผู้บริหารจะตัดสินใจผิด
เรื่องนี้แก้ทีหลังไม่ได้ เพราะข้อมูลซ้ำปนกับข้อมูลจริงไปแล้ว

## รูปแบบที่เสนอ

### ส่งข้อมูลเข้ามา

```
POST /api/v1/claim-batches
```

**Header**

| ชื่อ | จำเป็น | ความหมาย |
|---|---|---|
| `X-API-Key` | ใช่ | key ประจำโรงพยาบาล |
| `Idempotency-Key` | ใช่ | ค่าไม่ซ้ำต่อ batch ส่งซ้ำด้วย key เดิมจะไม่นับซ้ำ |

**Body**

```json
{
  "hospitalCode": "CA0032045",
  "scheme": "nhso-13f",
  "sourceSystem": "HOSxP",
  "sourceVersion": "3.68.2.14",
  "fund": "NHSO",
  "batchRef": "20260912-001",
  "submittedAt": "2026-09-12T09:15:00+07:00",
  "summary": {
    "total": 1250,
    "success": 1180,
    "failed": 63,
    "skipped": 7
  },
  "items": [
    {
      "vn": "680912001234",
      "an": null,
      "status": "1103",
      "nhsoUid": "bf680fd4-2c1a-4e3b-9a77-1234567890ab",
      "errors": []
    },
    {
      "vn": "680912001235",
      "status": "1101",
      "nhsoUid": null,
      "errors": [
        { "code": "C001", "field": "charge_code", "allowClaim": "N" }
      ]
    }
  ]
}
```

### ข้อกำหนดของแต่ละ field

| field | กติกา |
|---|---|
| `scheme` | ประเภทการส่งเคลม ต้องส่งมาเสมอ ห้ามปล่อยว่าง (ดูหัวข้อถัดไป) |
| `hospitalCode` | รหัสหน่วยบริการ ยาวไม่เกิน 9 ตัว ต้องตรงกับเจ้าของ API key (ดูหัวข้อถัดไป) |
| `status` | ต้องเป็นรหัสสถานะจริงของ สปสช. (ดู [nhso-status-codes](../domain/nhso-status-codes.md)) |
| `errors[].code` | ต้องเป็นรหัสข้อผิดพลาดจริง (ดู [nhso-error-codes](../domain/nhso-error-codes.md)) |
| `errors[].allowClaim` | `Y` หรือ `N` ตามที่ สปสช. กำหนดต่อรหัสนั้น |
| `items` | สูงสุด 1,000 รายการต่อ request |

## 🔴 `scheme` ต้องระบุมาเสมอ ห้ามเดาแทน

ระบบรองรับการส่งเคลมได้หลายประเภท แต่ละประเภทมีรหัสสถานะและรหัสข้อผิดพลาดคนละชุด

| ค่า | หมายถึง |
|---|---|
| `nhso-13f` | 13 แฟ้ม ส่ง สปสช. |

ตอนนี้มีประเภทเดียว แต่ **ถ้าไม่ส่ง `scheme` มาต้องปฏิเสธทั้ง batch**
ห้ามเติมให้เป็น `nhso-13f` อัตโนมัติ

เหตุผล: รหัส `C001` ของ สปสช. กับรหัสชื่อเดียวกันของหน่วยงานอื่นคนละความหมาย
ถ้าเดาผิดจะถูกนับรวมเป็นปัญหาเดียวกัน ตัวเลขบนแดชบอร์ดผิดแบบเงียบ ๆ ไม่มี error ให้เห็น
เหมือนกรณี idempotency key ข้างบน คือแก้ทีหลังไม่ได้เพราะข้อมูลปนกันไปแล้ว

## 🔴 `hospitalCode` มี 3 แบบ ห้ามตรึงรูปแบบ

กระทรวงสาธารณสุขออกรหัสให้หน่วยบริการ 3 แบบ
(ยืนยันจากทะเบียน hcode.moph.go.th ดึงเมื่อ 12 ก.ย. 2569 มี 44,374 แห่ง)

| แบบ | ตัวอย่าง | หมายเหตุ |
|---|---|---|
| รหัส 9 หลักใหม่ | `CA0032045` | ตัวอักษร 2 ตัว + เลข 7 หลัก **มีครบทุกแห่ง** |
| รหัส 9 หลักเดิม | `003204500` | ตัวเลขล้วน หน่วยที่ขึ้นทะเบียนใหม่ไม่มี |
| รหัส 5 หลักเดิม | `32045` | หน่วยที่ขึ้นทะเบียนใหม่ไม่มี |

**หน่วยที่ขอรหัสตั้งแต่ 1 เม.ย. 2568 เป็นต้นไป ได้เฉพาะรหัส 9 หลักใหม่**
ในทะเบียนมี 3,155 แห่งที่ไม่มีรหัสเก่าเลย เป็นคลินิกเอกชน 3,049 แห่ง
ถ้าระบบตรึงรหัส 5 หลัก หน่วยกลุ่มนี้จะส่งเข้าไม่ได้ทั้งกลุ่ม

ตัวอักษรนำหน้าผูกกับประเภทหน่วยงาน: `CA` คลินิกเอกชน · `GA` รพ.สต. และ อปท. ·
`EA` รพ.ชุมชน · `BA` สสอ. · `HA` รพ.เอกชน · `IA` ศูนย์วิชาการ · `FA` รพ.นอก สธ. ·
`AA` สสจ. · `CB` คลินิกเอกชน (ตัวสำรองเมื่อ `CA` ใกล้เต็ม)

🔴 **ห้ามเขียน regex ตรึงรายการตัวอักษรนี้** เพราะกระทรวงเพิ่มตัวใหม่เรื่อย ๆ
(`CB` มีแค่ 3 แห่ง คือตัวที่เพิ่งเริ่มใช้) ถ้าตรึงไว้แล้วเขาออกตัวใหม่
ระบบเราจะปฏิเสธข้อมูลจริงทิ้งโดยไม่มีใครรู้

ให้ตรวจแค่ 2 อย่าง: ยาวไม่เกิน 9 ตัว และ **มีรหัสนี้อยู่ในทะเบียนที่เราซิงก์มาหรือไม่**
ไม่ใช่ตรวจว่าหน้าตาถูก format

หน่วยเดียวกันอาจส่งคนละรหัสมาคนละครั้ง (ระบบเก่าส่ง 5 หลัก ระบบใหม่ส่ง 9 หลักใหม่)
ระบบจึงต้องเก็บครบทั้ง 3 ช่องแล้วจับคู่ได้ทุกแบบ ไม่งั้นหน่วยเดียวจะถูกนับเป็น 2 แห่ง

### 🔴 ห้ามส่งเข้ามาเด็ดขาด

ชื่อ นามสกุล เลขบัตรประชาชน ที่อยู่ เบอร์โทร วันเกิด
รหัสวินิจฉัยรายบุคคล ผลตรวจ รายการยา

ถ้าเจอ field พวกนี้ **ระบบต้องปฏิเสธทั้ง batch** ไม่ใช่รับแล้วค่อยกรอง
เพราะรับเข้ามาแล้วถือว่าเก็บแล้ว

### `hn` ต้อง hash ก่อนส่ง

ถ้าจำเป็นต้องส่ง ให้ hash ที่ฝั่ง รพ. ก่อน พร้อม salt ประจำโรงพยาบาล
ห้ามส่ง hn ดิบเข้ามา (ดูเหตุผลใน [decisions](../design/decisions.md))

## ตอบกลับ

**รับเรื่องแล้ว (202)**

```json
{
  "batchId": "01JBXZ9K2M4N5P6Q7R8S9T0V1W",
  "received": 1250,
  "duplicate": false
}
```

ตอบ 202 ไม่ใช่ 200 เพราะระบบรับเข้าคิวแล้วประมวลผลทีหลัง
ตอบเร็วทำให้ รพ. ไม่ต้องรอ และรองรับการยิงพร้อมกันได้มากขึ้น

**ส่งซ้ำด้วย key เดิม (200)**

```json
{
  "batchId": "01JBXZ9K2M4N5P6Q7R8S9T0V1W",
  "received": 1250,
  "duplicate": true
}
```

ตอบสำเร็จเหมือนเดิมแต่ไม่นับซ้ำ ฝั่ง รพ. จึงไม่ต้องเขียนโค้ดพิเศษ

**ข้อมูลผิดรูปแบบ (400)**

```json
{
  "error": "INVALID_PAYLOAD",
  "message": "พบข้อมูลส่วนบุคคลใน field ที่ไม่อนุญาต",
  "details": [{ "path": "items[3].patientName", "reason": "FORBIDDEN_FIELD" }]
}
```

## รองรับโหลด 5,000+ โรงพยาบาล

| ปัญหา | วิธีรับมือ |
|---|---|
| ยิงพร้อมกันตอนสิ้นเดือน | รับเข้าคิว (BullMQ) แล้วตอบ 202 ทันที |
| รพ. เดียวยิงถี่มาก | จำกัดอัตราต่อ API key |
| ข้อมูลซ้ำ | idempotency key |
| เขียนลงฐานข้อมูลไม่ทัน | เขียนเป็นชุดผ่าน worker ไม่เขียนทีละแถว |

## ยังไม่สรุป

- BMS Life ออก API key ให้ รพ. ยังไง หรือเราออกเอง
- ถ้า รพ. ส่งสถานะย้อนหลัง (รายการเดิมเปลี่ยนสถานะ) จะ update หรือเพิ่มแถวใหม่
- เก็บข้อมูลย้อนหลังกี่ปี
